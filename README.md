## 4. SLO / Threshold

Baseline туршилтын p(95) утга 270.72 ms гарсан тул уг утгыг үндэслэн SLO threshold-ийг ойролцоогоор 1.5 дахин нэмэгдүүлж тооцоолсон.

```
270.72 ms × 1.5 = 406.08 ms
```

Практик хэрэглээнд зориулж уг threshold-ийг 445 ms хэмжээгээр тохируулсан.

Ингэснээр ашигласан SLO дараах байдалтай болсон:

- **p(95) < 445 ms**
- **error rate < 1%**

Энэхүү threshold нь baseline утгаас хангалттай зайтай боловч latency хэт их нэмэгдвэл FAIL гарахаар сонгогдсон. Ингэснээр SLO-г зориудаар сулруулах бус, харин baseline хэмжилт дээр тулгуурлан бодит үндэслэлтэй босго тогтоох зорилготой юм.

## 10. Үр дүнгийн шинжилгээ

Ачааллыг 5 VU-ээс 30 VU, улмаар 100 VU хүртэл нэмэгдүүлэхэд throughput тогтмол өссөн үзүүлэлт үзүүлсэн. Тодруулбал, 5 VU-д 32.51 req/s байсан throughput 30 VU-д 200.20 req/s, 100 VU-д 653.76 req/s хүртэл нэмэгдсэн нь систем зэрэгцээ (concurrent) хэрэглэгчдийн ачааллыг сайн даах чадвартайг илтгэж байна.

p(95) latency-ийн хувьд 5 VU-д 231.28 ms, 30 VU-д 236.54 ms, 100 VU-д 244.04 ms гэсэн үзүүлэлт бүртгэгдсэн бөгөөд ачаалал ихсэх тусам latency зөвхөн бага хэмжээгээр нэмэгдсэн байна. 100 VU-ийн үед maximum latency 618.51 ms хүрсэн ч p(95) утга 244.04 ms-т хэвээр байсан нь ганц удаагийн өндөр latency-г бусад хүсэлтүүд дундажлан барьж байгааг харуулж байна.

Гурван түвшний аль алинд нь HTTP error rate 0.00% хэвээр хадгалагдсан бөгөөд p(95) latency 445 ms-ийн SLO threshold-ээс доогуур байсан тул бүх туршилт амжилттай PASS болсон.

Ийнхүү дүгнэвэл, test.k6.io систем нь 100 VU хүртэлх ачааллын түвшинд тогтвортой ажилласан гэж үзэж болно.

## 15. Дүгнэлт

Энэхүү лабораторийн ажлын хүрээнд Grafana k6 хэрэгслийг ашиглан веб системийн гүйцэтгэлийг ачааллын туршилтаар үнэлж, latency, throughput, error rate гэсэн гол хэмжүүрүүдийг судалсан. Туршилтыг 5, 30, 100 VU гэсэн гурван түвшинд тус бүрт 30 секундын хугацаагаар гүйцэтгэсэн.

Baseline хэмжилтэд үндэслэн тогтоосон 445 ms-ийн p(95) SLO threshold-ийг 5, 30, 100 VU-ийн бүх түвшинд амжилттай хангасан бөгөөд error rate-ийн SLO мөн бүрэн биелсэн.
